
# EvalForge 多实例请求路由决策

## V1 采用 Nginx 与 FastAPI 内部归属查询

Nginx 统一接收浏览器的 HTTP / SSE 请求和 Runner 的 WebSocket 连接。Runner 的有效会话归属由 Redis 记录。持有就绪 `RunnerSession` 的云端进程负责加载该 Runner 的 `ExperimentRuntime`。

### 请求如何到达归属进程

1. Runner 建立 WebSocket 时，Nginx 做普通负载均衡。收到连接的进程在 `hello` 注册时把 `cloud_instance_id`、`session_id` 和配置的 `cloud_route_id` 保存到该 Runner 的 Redis 会话记录。Runner 完成同步并进入 `ready` 后，该进程加载待运行的实验。
2. Nginx 收到需要定向的 HTTP 请求时，先通过 `auth_request` 发起一个内部子请求。子请求只传路由所需的路径信息，保留原请求体供后续业务接口使用。FastAPI 根据路径取出 `runner_id`，或根据 `experiment_id` 从 PostgreSQL 查询实验绑定的 Runner，再从 Redis 查询当前会话归属。
3. 内部接口返回目标上游标识。Nginx 根据部署时配置的实例与上游映射，把原请求直接交给目标进程。每个定向上游对应一个可直达的 Uvicorn worker。归属查询接口仅供 Nginx 内部调用，业务接口执行现有鉴权和权限检查。
4. 依赖本地运行时的接口通过 FastAPI 的路由依赖（`Depends()`）做入口兜底。只查本进程内存里的 `RunnerSession`、`ExperimentRuntime` 和接口所需的本地状态。查不到对象或本地状态不满足要求时，在执行业务前返回可重试错误。

多实例部署为每个可定向的 worker 设置唯一且稳定的 `EVALFORGE_CLOUD_ROUTE_ID`，例如 `cloud-a`。标识为 1～63 个小写英文字母、数字或连字符，首字符为字母或数字。单机开发可以留空，读取旧会话记录时也允许缺少路由标识。`cloud_instance_id` 仍标识本次启动的进程。

### 各接口的路由规则

| 请求 | 计划路由方式 |
| --- | --- |
| Runner WebSocket `/api/v1/runner/ws` | 普通负载均衡，连接建立后由接收进程注册会话归属。 |
| 创建实验 `POST /api/v1/runners/{runner_id}/datasets/{dataset_id}/experiments` | 强绑定。查询 Runner 归属，目标实例通过本地就绪会话校验后提交实验，再触发本地 Runtime 加载。 |
| 取消实验 `POST /api/v1/experiments/{experiment_id}/cancel` | 普通负载均衡，直接由后端保存取消意图。当前进程持有会话时可即时通知，离线 Runner 在下次 `runner.sync` 中收到取消指令。 |
| 订阅 Job SSE `GET /api/v1/experiments/{experiment_id}/jobs/{job_id}/events` | 强绑定。通过实验 ID 定向，只在建连时查询归属。后续片段从目标实例内存发送。Job 结果落库后结束流，浏览器通过详情接口读取结果。Runner 换实例时旧流结束，重新建连时查询新归属。 |
| 实验详情、Job 列表、评分结果 | 普通负载均衡，由任意实例从 PostgreSQL 查询。 |

### 后端与代理的接口约定

- Nginx 的 `internal` location 以 `GET` 调用 `/internal/runner-route`。它设置 `X-Original-Path` 为原请求的规范化路径（不含查询参数），并用 `X-EvalForge-Route-Token` 传入与各 worker 的 `EVALFORGE_INTERNAL_ROUTE_TOKEN` 一致的值。令牌留空时关闭查询。Nginx 以自身设置的请求头覆盖浏览器的同名请求头。
- 有有效且就绪的会话时返回 `204` 和 `X-EvalForge-Cloud-Route-Id`。Nginx 从响应头获取标识，通过部署配置里明确列出的上游映射转发。没有在线会话、尚未就绪或实验没有绑定 Runner 时返回 `403`。Redis、PostgreSQL 或会话路由标识不可用时，内部查询返回 `503`。`auth_request` 会将它视为子请求错误，部署时需在定向入口把这类代理错误映射成可重试响应。
- 新创建入口要求路径与请求体的 `runner_id` 一致，并通过 `Depends()` 检查本地 Scheduler 是否持有当前用户的就绪会话。会话缺失时返回 `503 runner_not_ready_here`。兜底只读本地内存，既有业务鉴权和创建逻辑照常执行。
- 浏览器使用定向创建路径。旧创建路径 `POST /api/v1/datasets/{dataset_id}/experiments` 保留兼容。启用内部归属查询后，旧路径也执行本地会话校验。

实际代理规则和 Compose 启动方式见 [云端部署](../deploy/README.md)。

## HAProxy 动态 Map 方案（暂缓采用）

以下内容保留为历史设计，供需要时重新评估。V1 以本页的 Nginx 方案为准。

### **一、核心架构决策**

**采用HAProxy动态Map + Redis归属记录 + Python业务实例本地校验。**

基本原则：

> Redis 保存当前有效的 Runner 会话归属。HAProxy 通过内存 Map 定位实例，实例入口的路由兜底只查本进程内存。

**EvalForgeWeb / Runner客户端**

HTTP / SSE / WebSocket

**HAProxy**

原生ACL + Converter + Map

通过内存映射选择目标实例

Python A

RunnerSession R001 及绑定 R001 的 ExperimentRuntime E123

Python B

其他 RunnerSession 及其 ExperimentRuntime

Python C

其他运行时对象

归属注册与变更

**Redis / 数据库**

Redis 保存当前 Runner 会话归属，PostgreSQL 保存实验绑定的 Runner。

**Python Owner同步逻辑**

Runner 建立或接管会话后，通过 Runtime API 增量更新 HAProxy Map。部署时指定一个实例运行定期同步，清理和修复 Map。

### **三、具体运行流程**

#### **1. RunnerSession建立**

```
Runner建立WebSocket连接
    ↓
HAProxy普通负载均衡
    ↓
请求进入Python实例A
    ↓
A创建RunnerSession
    ↓
A注册Redis Owner（R001 → A）
    ↓
触发HAProxy Map增量更新
    ↓
R001 → instance-A
    ↓
后续针对R001的定向请求直接进入A
```

首次连接不需要查Owner，因为此时还不存在归属。

#### **2. ExperimentRuntime建立**

```
实验提交后，持有该 Runner 就绪会话的实例加载实验
    ↓
在本地创建并注册 ExperimentRuntime
    ↓
后续按实验 ID 定位绑定的 Runner，再按 Runner 的当前归属路由
    ↓
订阅 Event、取消实验等请求进入当前持有 Runner 会话的实例
```

Runner 重连并进入 `ready` 后，由持有新会话的实例从数据库重建 Runtime。

#### **3. 正常HTTP/SSE请求**

```
请求到达HAProxy
    ↓
从URL提取资源标识
    ↓
查询内存Map
    ↓
直接转发Owner实例
    ↓
Python 从本进程内存查找对应 RunnerSession
    ├── 对象存在且本地状态满足接口要求 → 进入业务处理
    └── 找不到对象或本地状态不满足要求 → 返回可重试错误
```

只在依赖本地会话或 Runtime 的接口挂载 FastAPI 路由依赖（`Depends()`）。用请求中的资源 ID 查本地索引。手上只有 `experiment_id` 时，从本地 Runtime 索引定位对应的 RunnerSession；需要读取会话阶段时，也只读取本地字段。普通实验详情、Job 列表等查库接口照常处理。

这层校验只判断本进程是否还持有接口所需的对象。Redis 查询和 PostgreSQL 查询均放在各自原有的业务或同步流程中，路由依赖也不调用会查询 Redis 的 `RunnerSession.check_current()`。本地对象存在只代表通过本地校验，跨实例归属切换由会话生命周期和定期同步处理。

SSE连接只在建立时完成一次路由，后续Event沿着既有连接传输。

#### **4. Owner发生变化**

1. **Runner 断线。** 旧实例继续按现有逻辑，用 `compare_delete(runner_id, session_id)` 条件清理 Redis 会话。实例异常退出时，Redis 租约到期后记录失效。HAProxy Map 中的旧条目留给定期同步处理。
2. **Runner 建立新会话。** 新实例先注册 Redis 会话，再通过 HAProxy Runtime API 新增或更新该 Runner 的路由。发送更新前核对 `session_id`，增量更新失败时，重试根据 Redis 当前归属生成操作。
3. **旧会话的关闭回调晚到。** 例如 A 的旧会话是 `s1`，B 已注册新会话 `s2`。A 的 Redis 条件删除会因 `session_id` 不匹配而跳过。A 的关闭回调无需操作 HAProxy Map。

#### **5. 定期同步**

V1 通过环境变量指定同步实例。配置项暂命名为 `EVALFORGE_HAPROXY_MAP_SYNC_ENABLED`，默认 `false`。同一套部署中只给一个实例设为 `true`，该实例启动一个 `asyncio` 定期同步协程。设为 `false` 的实例跳过协程启动，仍负责各自的新会话增量更新。建议先按 30～60 秒的间隔做对账，具体周期联调时确定。

- Redis 有有效会话时，将 HAProxy Map 修正为该会话的当前归属，补齐缺失条目。
- Redis 确认无有效会话时，清理遗留条目。删除前重查一次。删除后如果发现 Runner 已注册新会话，立即按最新归属补写。Redis 查询失败时，本轮跳过该条目的删除。
- Redis 注册与 HAProxy Map 写入之间可能短暂不一致。依赖本地运行时的请求落到旧实例时，若本地对象已清理或已标记关闭，入口返回可重试错误。旧对象尚未清理时，本地检查可能通过。后续会话清理和定期同步会更新本地对象和 Map。

被指定的实例停机后，可由部署侧改配其他实例接手。自动选举和故障接管列为 TODO。

### **五、还没有完全敲定的实现细节**

为了防止后续开发时把建议误认为决定，我另外标注三个尚未最终选定的点：

- **Map Key格式：** 倾向使用`runner:R001`、`experiment:E123`这种资源类型加ID的精确匹配，而不是完整URL。
- **增量同步执行者：** 倾向由Python统一封装同步组件，但尚未决定是由业务实例直接调用，还是交给统一Controller串行执行。
- **异常请求如何恢复：** 确定不能随机转发，暂未确定具体错误码、重试机制和修复通知协议。

这些都可以等真正开始写对应模块时再确定。

### **六、当时采用的架构原则**

我觉得我们可以暂时把以下六点作为后续开发的约束：

1. **有状态对象必须有明确Owner。** RunnerSession和ExperimentRuntime都遵循这一原则。
2. **请求由HAProxy直接路由Owner。** 不再采用业务实例之间的HTTP二次代理作为常规入口方案。
3. **路由和入口兜底都只查内存。** HAProxy 查 Map，实例查本地 RunnerSession 和接口所需的运行时对象。
4. **新会话建立或接管后主动更新 Map。** 断线保留路由条目，由定期同步清理和修复。
5. **本地校验失败时在业务执行前返回可重试错误。** 定期同步负责修复 Map。
6. **部署时指定一个实例运行定期同步协程。** V1 通过环境变量配置，Leader Election 和自动接管列为 TODO。

还有一条边界保持不变：**HAProxy解决的是客户端请求路由问题，不会自动解决不同Owner实例之间的Runner指令和执行结果传递。** 那属于另一条通信链路，我们暂时不展开。

整体上，我认为方案已经可以定下来了。

V1 验证两条链路。Runner 重连接管后，新路由应生效，旧会话晚到的关闭回调应保留新路由。Runner 离线后，定期同步应清理旧条目。清理与重连相遇时，路由应恢复为最新归属。
