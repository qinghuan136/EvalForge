# 客户端取消与恢复（第三步）

本阶段只停止客户端对 Agent 的 HTTP 等待，不调用 Agent 的取消接口。单 Job 容量和现有表结构保持不变。

## 取消链路

```text
jobs.cancel / sync.cancel
  → Session 校验、定位 Attempt
  → JobManager.cancel 创建独立取消控制任务
  → request_cancel 提交首次取消意图及原因
  → accepted：保存 cancelled + pending，不调用 Agent
  → running：取消 HTTP Task，由执行协调协程保存 cancelled + pending
  → 终态：保留结果
  → unknown：仅保留意图，不伪造已停止
```

取消响应 accepted=true 表示请求已持久化、已交给本地处理，不保证远端停止，也不保证最终一定为 cancelled。结果照常由 Session 扫描、发送 complete、收到 ACK 后更新 acknowledged。

## 两个执行 Task

| 对象 | 职责 | 用户取消时 |
| --- | --- | --- |
| `_task` | 取得执行权、等待 HTTP、保存最终结果 | 不直接取消 |
| `_http_task` | HttpExecutor.execute，管理一次 HTTP 请求及响应资源 | 只对尚未结束且未在取消中的任务发送 cancel |

启动执行与取消共享 Manager 锁，保护 claim 提交到 HTTP Task 创建之间的窗口。锁不跨 HTTP 等待持有。

HTTP Task 的 CancelledError 传给协调协程；协调协程读取持久化取消意图，生成取消结果。重复取消不能再次打断 HTTP 的 finally/aclose。

HTTP 已经返回结果时，取消不会中断保存；已经提交的最终结果不可重写。HTTP 超时仍是 failed/timeout，不混为用户取消。

取消控制 Task 用 shield 隔离 RPC 处理协程的取消，并由 Manager 保留引用、回收和观察异常；因此 Session 断开不会撤销本地取消处理。存储异常沿用停止接收新任务的策略。

## 退出与重启

退出时 Manager 先关闭接单、停止 HTTP 等待，再等待执行与取消控制任务结束，之后关闭 HTTP 客户端和数据库。

- 正在保存已获得的结果：等待保存完成。
- 退出中断 HTTP 等待：保留 running，不能当作用户取消。
- 下次启动只调用一次 recover_interrupted，将遗留 running 转成 unknown。

| 重启后的记录 | 后续动作 |
| --- | --- |
| accepted、无取消意图 | 等云端 continue 后执行 |
| accepted、已有取消意图 | 在 continue/cancel 处理中生成取消结果，不调用 Agent |
| 原 running → unknown | 不自动执行；cancel 仅保存意图 |
| succeeded/failed/cancelled + pending | 按 retry_upload 重传保存的同一结果 |
| acknowledged | 不再上报 |

普通断线不会关闭 Manager，也不会调用启动恢复。重连 sync 的 continue 复用仍存活的执行，cancel 停止其 HTTP 等待；同步期间刚完成的结果仍按原有扫描链路上报。
